# AUDIT-2026-10

5 October 2026. Audit of [cockaigne_sensing](https://github.com/5amleach/cockaigne_sensing/tree/b1e654633c45731538130e3aaeb1300e41c4e580), commit `b1e654633c45731538130e3aaeb1300e41c4e580`.

**Verdict.** This repository is not ready to run an unattended installation for a month. It contains working components and useful short tests, but no live launcher joining the cameras to the bus, no automatic restart after a process dies, and no startup arrangement after a machine reboot. The default camera calibration is missing. Some promised safeguards are incomplete, and some incorrect results look entirely normal to the rest of the system. A moving wall would not prove that the installation was sensing the room or making the intended decisions.

The test suite passes: **56 passed in 25.43 seconds, exit code 0**. Additional checks reproduced failures outside the suite's coverage, including a bus reader that dies without a fault log, a supposedly valid clip pool that crashes the controller, and a blind controller moving up a ring. Passing the current tests is not evidence of unattended readiness.

**What I examined.** I cloned the public repository, read the seven requested root documents in the requested order, then all 37 Python files in the two packages and all seven Python test files. I also read the controller brief, configuration, packaging file, ignore file and three bench reports; parsed and checked every record in both committed track recordings; and viewed both plan images. There are 66 tracked files. The file inventory below gives their line counts. In shorter sensing references, `capture/`, `detect/`, `floor/`, `features/`, `actions/`, `bus/` and `tools/` are folders inside `cockaigne_sensing/`. A ring is the work's level from Barren to Ring 4; an arm is one of its eight visual themes. The bandit is the learning chooser that ranks those themes. File references such as `cockaigne_controller/run.py:154` refer to the audited commit, not a later version of the repository.

No repository source or test was edited. Reproduction scripts, dependencies and test outputs were kept outside the clone. This is a source audit and a desk test on Windows, not a camera, GPU, actual Resolume, power-cut or month-long soak test. The separate data-wall project, actual composition, installed camera settings, detector weights and Windows startup configuration are not in this repository. I cannot infer their behaviour from files that are absent.

**The five things to fix first, in order.**

1. **Build and supervise the actual show startup.** There is no live camera-to-bus launcher: the available floor, feature and bus commands read files (`cockaigne_sensing/floor/run.py:89–117`, `features/run.py:20–48`, `bus/run.py:28–59`). Only one camera is configured, and its calibration file is absent (`config/sensing.yaml:11–24`). There is no checked-in service, scheduled startup task or watchdog to restart any process. Resolume being unavailable during startup ends the controller instead of being retried (`cockaigne_controller/run.py:139–147`; `cockaigne_controller/resolume.py:54–58`). Until these are handled, a reboot or ordinary crash can end the show for the rest of the month. The acceptance test should start from a powered-off machine, then kill each process in turn and verify automatic recovery and a visible fault report.

2. **Make camera and message health explicit, and repair the blind fallback.** Camera retries have no log or per-camera health output (`capture/source.py:62–70`). A stream repeatedly supplying old pictures can receive fresh arrival timestamps (`capture/source.py:72`). The controller checks when messages arrive, not whether the measurements are new (`cockaigne_controller/loop.py:65–96`). A malformed message can permanently end its unsupervised reader task (`cockaigne_controller/run.py:110–118,154,197–198`). Worse, its blind fallback lowers the last requested ring rather than the ring actually showing (`cockaigne_controller/loop.py:149–175`): with the wall at Machinery 1 and the last request at Ring 4, I reproduced a blind move to Machinery 2. A failed sensor must not masquerade as an empty or healthy room, and the safe descent must follow the actual wall position.

3. **Make a clip decision mean a clip actually started, and validate every permitted move.** The controller advances its internal position before sending the clip command (`cockaigne_controller/loop.py:176–188`). Confirmation failure does not undo this or mark the decision failed (`cockaigne_controller/run.py:64–88,178–191`). Its startup checks can accept a pool that immediately crashes on a Barren probe; I reproduced this by removing `b_b` and `b_m1` from the test pool. The validator reported no missing clips, then `decide()` raised `KeyError: None`. Routes can also leave the requested ring while it is supposed to be held. Resolve these behaviours before trusting the ledger, recovery after a Resolume restart, or learned rewards.

4. **Prevent a failed listener or bad message from breaking delivery, and make losses countable.** The bus suppresses send exceptions (`bus/publish.py:55–61`), sends nothing to absent clients, retains no last state, and waits for all current sends before advancing. The controller's reader catches connection failures but not malformed content or every connection-setup failure. A slow listener can delay sensing delivery; a bad message can stop reception permanently. Add bounded delivery, message validation, a supervised reader, explicit loss/age reporting and a recovery snapshot. Rehearse a disconnected, slow and malformed-message client, not just a healthy local connection.

5. **Prove the measurements and rehearsal inputs are truthful enough for the artwork.** The floor merger cannot distinguish two nearby people from two views of one person; calibration dimensions are ignored; and changing camera view can look like a change in mood (`floor/tracker.py:19–25,54–75`; `floor/homography.py:15–17`; `features/person.py:86–122`). The combined fake day has duplicate IDs and people who never leave. At its end I measured two people, both ID 1, and only one mood counted. A first seated visitor can add 12.25 to Furniture's choice score while every random draw is between 0 and 1 (`cockaigne_controller/bandit.py:93–118`), overwhelming the purported gentle lean. Correct the rehearsal, validate calibration against measured positions at the final camera height, and test these decisions against recorded expected behaviour. Otherwise the installation can run continuously while making false claims about its audience.

**Where the documentation and code disagree.** These are comparisons with the executable behaviour. Short quotations identify the exact claim and the code responsible. Where a later decision already acknowledges a limitation, that does not make the older guide accurate.

- **D1 — Four-camera capture is described as present.** `GUIDE.md:7` says “Opens the four infrared cameras”. The code defines `class FrameSource:` (`capture/source.py:34`) for one supplied address; the supplied camera list has only `name: cam1` (`config/sensing.yaml:14`). There is no caller that opens the configured set and runs the live chain. `RUNBOOK.md:11` correctly admits the missing launcher. The guide describes a completed system that is not supplied.

- **D2 — The architecture describes the old cohesion formula.** `ARCHITECTURE.md:41` says the three signals combine by “geometric mean”. The selected inputs are actually `[clustering, coordination]` (`config/sensing.yaml:43`), with `return stillness + (1.0 - stillness) * synchrony` in `features/crowd.py:99`. Stillness and synchrony are combined first. The result is then blended with occupancy-dependent proxies and capped (`features/crowd.py:241–252`). `CONTRACTS.md:57` and the later decisions describe this newer behaviour; the architecture has not caught up.

- **D3 — Arousal has fewer inputs than the architecture promises.** `ARCHITECTURE.md:43` includes “acceleration and vertical bounce”. The implemented arousal is `speed / self.cfg["arousal_speed_full_mps"]` (`features/person.py:113`). Acceleration affects valence, not arousal; bounce is not measured. This limitation is acknowledged in `DECISIONS.md:53`.

- **D4 — The picture-handling boundary is not enforced as written.** `ARCHITECTURE.md:74` says “No module below `capture` receives a frame except `actions`”. Detection explicitly accepts `frame: np.ndarray` (`detect/tracker.py:45`), and the bench tool copies and saves full frames: `cv2.imwrite(str(out / f"snap_{sec:04d}s.jpg"), ann)` (`tools/bench_detect.py:80`). That tool has no `--record` option and saves snapshots by default. Detection plainly needs pictures; the stated rule contradicts both the design and the implementation. The bench command can also accept an RTSP address through `FrameSource`, so its being called a development tool is not an enforced restriction.

- **D5 — Adjustable thresholds also live in code.** `ARCHITECTURE.md:47` promises “Every threshold” in sensing configuration. `FloorStage` instead defines `bucket_s: float = 0.1, margin_m: float = 0.3` (`floor/run.py:33`), and the tracker defines `gate_m=1.2` (`floor/tracker.py:44`). Other examples are the five-second detector memory, half-second camera retry, fixed velocity smoothing, and REST timeouts (`detect/tracker.py:65`; `capture/source.py:66`; `floor/tracker.py:142–144`; `cockaigne_controller/resolume.py:56,63`). Several affect behaviour on site and cannot be changed through the promised configuration files.

- **D6 — Action recognition is a brief, not an implementation.** `ARCHITECTURE.md:51` says “Runs through Ollama”. `cockaigne_sensing/actions/__init__.py:3` says “NOT YET WRITTEN.” It contains no executable action-recognition code. The floor emits zeros for phone, drink and eat (`floor/tracker.py:162`). `GUIDE.md:31` and the README status are accurate about this absence.

- **D7 — Arm-specific audio does not start.** `GUIDE.md:47` says “Audio stems for the next arm start”. The only audio action is `resolume.set_volume(layer, volume)` (`cockaigne_controller/audio.py:16`). It changes four bank-A volumes to the same value. It does not select a stem, start a clip, use the chosen arm, operate bank B or crossfade. The function receives only a ring, so it cannot implement the guide's claim. The brief and README acknowledge that audio is a stub.

- **D8 — Holding a ring need not stay on it.** `GUIDE.md:47` describes holding a ring as “sideways”. Routing can instead choose `self.map.next_step(frm, target)` (`cockaigne_controller/loop.py:175`), without restricting the path's rings. With the repository's own test pool, Machinery 1 targeting Storm 1 first went to Barren. Machinery 4 targeting Architecture 4 first went to Machinery 3. Both are valid results of the implemented shortest-path rule. The guide's promise requires a stronger route rule than the code supplies.

- **D9 — Delivery to every listener is not guaranteed.** `GUIDE.md:37` says listeners “receive everything”. Sending uses `return_exceptions=True` (`bus/publish.py:61`), and no result is inspected. With no targets there is no send at all. There is no saved last message or missed-message replay. I supplied a client whose send raised an error: publication returned normally and the failed client remained in the set in that isolated check. A real connection handler may later remove a closed client, but that does not report or restore the lost message.

- **D10 — Reconnection is not unconditional.** `GUIDE.md:39` says the controller “reconnects every five seconds”. The reader handles only `except (OSError, ConnectionClosed):` (`cockaigne_controller/run.py:114`). A JSON parsing error or missing required crowd field escapes, ends the reader task, and prevents further attempts. The main loop does not inspect that task. Five seconds is also the pause after a handled failure, not a maximum recovery time including connection and handshake delays. `RUNBOOK.md:17` says “everything retries”, but the initial `layout = resolume.read_layout()` (`cockaigne_controller/run.py:140`) has no retry at all.

- **D11 — The no-crash fire guarantee is false.** `RUNBOOK.md:39` says “never crashes”. The initial `resolume.fire_clip(layer, index)` (`cockaigne_controller/run.py:69`) and retry at line 86 are outside the exception handler. I made the send raise `OSError`; it escaped the function. REST errors are caught and logged, but on a REST error the function returns without the advertised refire. The repository's own test expects that one-send behaviour (`tests/test_controller.py:229–235`).

- **D12 — The people identity contract is violated by the recommended rehearsal.** `CONTRACTS.md:36` says “`id` is stable across the whole room and all cameras.” The fake output uses `"id": a.pid` (`tools/fake_room.py:140`), while `day()` concatenates actors from scenarios reusing the same IDs without ending all their earlier lifetimes (`tools/fake_room.py:113–120`). Multiple simultaneous people can therefore carry ID 1. The floor tracker also provides a best-effort identity estimate, not a guarantee through crossings or long outages (`floor/tracker.py:79–108`).

- **D13 — Mixed rehearsal timestamps do not share the promised file clock.** `CONTRACTS.md:5` describes “frame's time within the file”. The live controller takes `now = time.monotonic()` (`cockaigne_controller/run.py:161`) even when its input is a replay, while replayed people and crowd messages retain their original `t`. A mixed bus recording would need an explicit time conversion; it cannot be assumed to be a single coherent recorded timeline. Separately, decisions are normally dated when planned at the audio lead, about five seconds before they are sent (`cockaigne_controller/run.py:192–195`; `cockaigne_controller/loop.py:181`).

- **D14 — Bus recording misses messages from clients.** `CONTRACTS.md:88` describes recording “Every message above”, which includes decisions. The bus recorder is only in `for msg in replay(path):` and `recorder.write(msg)` (`bus/run.py:43,52`). Client messages take a different path through `await self._send_all(data, exclude=websocket)` (`bus/publish.py:47`) and never reach that recorder. The controller can record its own decisions separately, but bus `--record` is not a recording of the whole installation.

- **D15 — The reservoir is not persistent.** `GUIDE.md:25` says it “never resets”. Each new `Reservoir` starts with `self.level = 0.0` (`features/crowd.py:168`); there is no saved state. It survives occupancy changes within one process, not a process restart or reboot. That distinction matters during a month-long show.

- **D16 — A controller crash does not establish what the picture will do.** `GUIDE.md:49` says the wall “freezes”. The actual code calls `self._osc.send_message` and leaves playback to Resolume (`cockaigne_controller/resolume.py:67–68`). A dead controller means no more scheduled commands from it. Whether the existing clip continues, loops, ends, holds a frame or becomes blank depends on the absent composition and playback settings. The code cannot support the guide's categorical visual diagnosis.

**Silent failures, silent losses and believable but wrong values.** This catalogue covers the mechanisms I found in the checked-in code. Some are deliberate filters; the problem is that the output does not distinguish a deliberate omission from bad sensing. It does not claim to enumerate hidden failures inside OpenCV, a GPU driver, the operating system or Resolume.

1. **Camera loss and file damage have no useful completion report.** Live reopen attempts are unlogged. A failed recorded-file read simply returns, treating a damaged/truncated file like an ordinary end. An initial open failure is different: it raises a visible error. The error includes the original address, which could include camera credentials. Evidence: `capture/source.py:47–54,62–74`.

2. **Old pictures can be presented as fresh observations.** Live timestamps are assigned on receipt, with no comparison of camera timestamps or picture content. The request for a one-frame buffer ignores whether the backend accepted it and is not repeated after reconnect. A failed frame-rate reading silently becomes 25 fps for a file, potentially changing every recorded time. Sources other than addresses beginning with `rtsp://` are treated as files. Evidence: `capture/source.py:46,50–56,68–73`. Whether the installed backend actually buffers or blocks needs a real-camera test.

3. **Detection omissions look like absence.** New tracks younger than the threshold are silently withheld. Results without tracker IDs produce an empty list, and old IDs are forgotten after a hard-coded five seconds. There are no counts explaining rejection, tracker uncertainty or camera coverage in the emitted message. A low-confidence real visitor and a genuinely empty frame can therefore look the same downstream. Evidence: `detect/tracker.py:47–68,71–79`. The age filter is intentional, but has no accompanying health measure.

4. **No calibration can become an empty room.** `FloorStage` quietly loads only calibration paths that exist; unknown cameras then produce no sightings. The floor command prints one startup warning for configured missing cameras, but the class itself does not, and unexpected camera names get no warning. The supplied default loads zero homographies. Running from a different working directory can also make existing relative paths appear absent. Evidence: `floor/run.py:43–56,98–100`; `config/sensing.yaml:18`.

5. **The wrong calibration can remain numerically plausible.** Loading reads only the matrix; saved camera name, source image size, fitting method and error estimates are ignored. Track-message width and height are not used to rescale or check it. A 4K calibration used on a sub-stream can discard real people or place them at wrong but accepted coordinates. In my check, a real floor point at (3, 6) metres disappeared after its pixels were reduced to 640×360 while retaining the 4K matrix. Evidence: `floor/homography.py:15–17`; `floor/run.py:52–68`; `config/homography_venueA.json:2–7,25–36`.

6. **Filtering conceals the cause of lost people.** Polygon rejection, off-floor rejection and a projection with a zero divisor produce no diagnostic counts. The last returns not-a-number coordinates, which the floor bounds check rejects. A 0.3-metre margin also permits observed people outside the stated floor rectangle, whereas predicted positions are clipped inside it. Evidence: `floor/homography.py:26–31`; `floor/run.py:33,60–67`; `floor/tracker.py:128–133`. These are differing rules for observations and predictions, not proof that all accepted positions are correct.

7. **Two nearby people can become one.** A `Sighting` has no camera name or original track ID. The merger absorbs every nearby sighting, including two distinct people seen by the same camera, and also repeated sightings from one camera within a bucket. I supplied two people 20 cm apart and got one. The code was also intended to remove duplicate detector boxes, but cannot distinguish that case from genuinely close visitors. Evidence: `floor/tracker.py:19–25,54–78`; `floor/run.py:67,77`. The resulting lower headcount remains a perfectly ordinary number.

8. **People can silently exchange identities.** Matching is greedy by distance from a predicted position. Crossings, occlusion and calibration errors can attach a sighting to another person's history. Predicted people are published with no indication that they have not just been seen, no observation age and no confidence. The original detection confidence is used during merging but not carried into the people message. Evidence: `floor/tracker.py:79–118,121–144,153–165`. Mood, dwell time and action histories can consequently belong to the wrong visitor.

9. **A supposedly expired person can return with an old age.** Expiry is checked after matching and updating the last-seen time. When no updates happen during a long gap, a new sighting can refresh an old track before it is expired. I observed at time 0, sent nothing for an hour, then observed the same position: it retained ID 1 and an age of 3,600 seconds despite a three-second drop setting. Evidence: `floor/tracker.py:81–108,135–144`. A long gap can also leave the previous velocity in place when the refreshed history is too short to recalculate it.

10. **Time grouping has no independent clock or order check.** A floor bucket is flushed only by a sufficiently later message or an explicit `flush()`. If input stops, the final bucket stays pending; coasting and expiry do not advance by themselves. Backward or badly interleaved timestamps can keep unrelated observations in a bucket and match them as one instant. The bucket does not require one message from each expected camera. Evidence: `floor/run.py:70–86`. The future launcher would have to supply the missing ordering and timed flushing.

11. **Slow, duplicated or backward input distorts time-based scores.** Feature updates cap each elapsed interval at one second. After ten seconds without input, the reservoir and averages advance by at most one second. A backward timestamp updates the remembered previous time but can suppress crowd output until the old emission time is reached again. No warning identifies either case. Evidence: `features/crowd.py:210–219,250–258`. This also means ten-second and per-second descriptions are only reliable at the expected input rate.

12. **Plausible mood labels can be false with no uncertainty attached.** A smaller rectangle can mean movement away from a camera, a camera switch, a cut-off body or occlusion; the scorer interprets shrinkage as slump until its height reference catches up. At rest, an ordinary full-height rectangle initially gets positive valence and a happy label. The neutral middle keeps the previous label. There is no unknown category or confidence. The eight-second rule holds an existing label for eight seconds; it does not require eight seconds of evidence for the new label. Evidence: `features/person.py:86–122,139–156`. The bench report already records saturated negative valence from non-mood causes (`bench/2026-10-05-features-on-venue-clip.md:26–28`).

13. **Missing action recognition is indistinguishable from nobody acting.** Phone, drink and eat are initialized to zero and never populated by a built recognizer. Feature and controller code also substitute zeros for several missing action fields. A stale upstream action value is not given an expiry time. Evidence: `actions/__init__.py:1–33`; `floor/tracker.py:162`; `features/crowd.py:260–285`; `cockaigne_controller/bandit.py:98–109`. Reporting zero is an explicit current design choice, but there is no field telling the data wall that this measurement is unavailable.

14. **The action lean can make the choice certain.** An initial seated person produces sitting fraction 1 divided by baseline floor 0.02: rate 50, excess 49, then weight 0.25 gives 12.25 in the solo band. The learned random scores range between 0 and 1. Furniture then wins regardless of those scores. There is no cap on the final lean. Moreover, decay happens only in `observe()`, so it freezes while messages are absent; daily belief reset does not clear it. Evidence: `cockaigne_controller/bandit.py:60–65,93–118`; `cockaigne_controller/loop.py:100–112`; `config/controller.yaml:43–48`. The test called `test_bias_leans_on_close_calls_but_cannot_overturn_conviction` only tries a much smaller “realistic” value in its second half (`tests/test_bandit.py:44–53`).

15. **Received does not mean current.** Every accepted crowd message refreshes the controller's receipt timer, even if its original timestamp is repeated or far behind. I replayed the same time-zero crowd state with a new receipt time: the controller considered it fresh. There is no message sequence, sensor-health field, schema check or cross-check between headcount and action/mood counts. Evidence: `cockaigne_controller/loop.py:65–96`. Replaying a recording is intentionally possible, but live and rehearsal freshness are not distinguished.

16. **Malformed values can evade ordinary range expectations.** There is no explicit finite-number validation before arithmetic or JSON publication. Python's JSON handling admits non-finite values by default, and expressions such as `max(0.0, min(1.0, v))` can turn not-a-number into an apparently valid endpoint rather than a fault. Configuration is also returned without structural or numerical validation. Evidence: `features/crowd.py:36–44`; `features/person.py:21–22`; `cockaigne_controller/bandit.py:22–38`; both `config.py` loaders. Other malformed values raise instead; those errors are not reliably supervised. A range-looking output alone does not prove good input.

17. **The bus loses messages without a delivery log.** A send to zero listeners is a no-op. Send exceptions are collected and ignored. There is no per-client loss count, backlog or replay on reconnection. A newly connected data wall or controller cannot learn the last state until another suitable message arrives. Evidence: `bus/publish.py:30,40–61`. The bus starts a recording immediately, so the beginning can pass before the operator starts the other terminals (`bus/run.py:32–50`).

18. **A slow listener can hold up everybody.** Publication awaits all target sends with no application deadline or independent client queue. The recording loop cannot proceed until publication returns. Incoming client rebroadcasts can also overlap outgoing publications without a single ordered application queue. Evidence: `bus/publish.py:46–61`; `bus/run.py:49–52`. Underlying WebSocket limits may eventually close a stalled connection, but the repository does not define a maximum delivery delay or log that delay.

19. **The controller can keep running after its reader dies.** Raw client data is rebroadcast without inspection. A malformed JSON message, valid JSON of the wrong shape, a missing required crowd field, or an unhandled connection-setup error can terminate `keep_connected()`. The parent retains the task but never checks or awaits its result while running. In my malformed-JSON check, the task ended with `JSONDecodeError`; its only log was the initial connection message, and `self.ws` remained assigned. The main controller can later report blindness, but not the actual cause or a successful restart of this dead reader. Evidence: `bus/publish.py:40–47`; `cockaigne_controller/run.py:110–118,154,197–198`.

20. **Some decision loss is logged, but never repaired.** When the bus is absent or closes mid-send, warnings are emitted. They do not include the lost decision's identity and no queue retries that decision. A successful socket write is not an acknowledgement that the data wall received or displayed it. Evidence: `cockaigne_controller/run.py:120–128,178–191`. This is not an ignored exception; it is an acknowledged loss with incomplete recovery and incomplete attribution.

21. **The bus's record and event derivation omit its return traffic.** Client messages bypass both the recorder and `LedgerEvents.observe()`. Thus client decisions are absent from bus `--record`, and people/crowd messages injected over the socket do not create the corresponding bus ledger events. The controller writes its own decisions/outcomes directly, which covers that specific writer only. Evidence: `bus/publish.py:46–47`; `bus/run.py:43–52`; `cockaigne_controller/run.py:181–188`.

22. **UDP audio changes have no confirmation; video checks can report a false success.** A volume send is fire-and-forget. Video confirmation checks the connected numerical slot, not its name, content, playback progress, output visibility or whether a loop clip actually restarted. If an old clip already occupies the intended connected slot, a lost re-trigger can pass confirmation. After a REST error or persistent mismatch, the function returns without a success/failure result and the caller still publishes and logs the decision as fired. Evidence: `cockaigne_controller/resolume.py:31–43,60–71`; `cockaigne_controller/run.py:64–88,178–191`. Warnings exist for detected REST problems; silent wrong-content and already-connected cases are not checked.

23. **The layout can silently select the wrong asset or layer.** Unparseable names are ignored. Duplicate names or alternate spellings for the same move retain one entry without a warning. All layers are scanned, and the configured `video_layer` is never consulted. There is no confirmation that the expected movie file is available or 60 seconds long. Evidence: `cockaigne_controller/resolume.py:20–28`; `cockaigne_controller/clipmap.py:33–63`; `cockaigne_controller/run.py:51–61`; `config/controller.yaml:11,18`. The supplied API parsing is tested against invented JSON, not a committed capture of the actual composition.

24. **Validation permits runtime gaps and unintended routes.** `missing()` checks Ring 4 loops, Ring 2/3 collapses and general reachability. It does not require every direct Barren probe that `decide()` assumes, or ring-preserving lateral paths. It also hard-codes four rings in part of its validation despite a configurable ring count. Evidence: `cockaigne_controller/clipmap.py:96–116`; `cockaigne_controller/loop.py:158–177`. A missing Barren loop is intentionally allowed and causes repeated excursions rather than settling permanently in Barren.

25. **A planned state is treated as the displayed state.** `decide()` changes the current node at the audio lead. New crowd input during the five seconds before firing does not revise the pending decision. The decision time is also the planning time. If OSC fails or the actual composition disagrees, the controller still plans subsequent clips from its imagined destination. Evidence: `cockaigne_controller/loop.py:147–188`; `cockaigne_controller/run.py:171–195`. Ledger ring records use the requested ring even when the path is currently at a different ring; this can misdescribe the displayed state (`cockaigne_controller/run.py:184–186`).

26. **Learning can be based on missing or unsuccessful experience.** Rewards are settled when the next decision is planned, usually at 55 seconds, omitting the last five seconds described as part of the clip's outcome. A previously opened reward window can settle against stale cohesion after sensing fails. A clip that was never confirmed can still receive a reward. A reward window that never opens is simply discarded, with no “not enough evidence” ledger entry. Old pending reward and action state also cross midnight. Evidence: `cockaigne_controller/loop.py:78–83,100–131,149,187–188`; `cockaigne_controller/run.py:192–195`.

27. **The supplied full-day rehearsal is internally inconsistent.** `Actor.leaves` defaults to infinity. The lone and sitting scenarios never set an end time; `day()` shifts them without imposing scenario boundaries and without renumbering IDs. The result lasts 490 seconds, not the 450 stated in its introductory comment, contains duplicate IDs in 2,681 of 4,901 messages, and ends with two ID-1 people. The mood dictionary has one key per ID, so its count can be smaller than headcount. Evidence: `tools/fake_room.py:15,45–46,63–69,72–78,96–100,113–120,139–152`; `features/person.py:57–63`. The tests exercise the four separate scenarios, not `day()` (`tests/test_fake_room.py:40–63`).

28. **Development output can silently accumulate old runs.** `Recorder` always appends. Rerunning a command with the same output path combines sessions whose timestamps and IDs can start over. Replaying that combined file does not detect the clock reset. The recorder does not flush after each message, so a crash can lose its buffered tail. A malformed last line then stops future replay, rather than being diagnosed as a recoverable partial record. Evidence: `bus/record.py:21–29,42–57`; recording calls in `floor/run.py:101`, `features/run.py:29`, `tools/fake_room.py:166` and `tools/bench_detect.py:52`.

29. **The ledger has no durability or shared-writer protocol.** It opens an append-mode text file and flushes each entry, but performs no disk-sync operation, inter-process locking, sequence numbering or partial-line repair. Bus and controller write from separate processes. Their claim that a one-line append is safe is not established by a concurrency or power-loss test. I am not claiming that ordinary writes necessarily interleave; I am saying that their integrity across Windows failures is unproved. Relative ledger paths can also put the two writers in different files if started from different folders. Evidence: `bus/ledger.py:23–36`; `config/sensing.yaml:93`; `config/controller.yaml:61`; `tests/test_bus.py:22–32` tests sequential reopening only.

30. **Log growth and disk failure have no operating policy.** The controller uses an ordinary file handler without rotation, retention or free-space monitoring; the ledger grows indefinitely. A ledger write error can propagate out of the show loop. Some uncaught failures produce only a terminal traceback; there is no top-level controller exception logger or external alarm. Evidence: `cockaigne_controller/run.py:41–48,181–201,211–214`; `bus/ledger.py:31–32`; `bus/run.py:49,55–59`. Month-long ordinary log volume need not be huge, but a full disk or repeated failure has no tested containment.

31. **The supplied bus can finish normally and disappear without an end message.** With no `--loop`, reaching the recording's end closes the bus, ledger and recorder; there is no completion log. With `--loop` and an empty recording, the outer loop repeats without any awaited operation, potentially consuming a CPU core and preventing normal async progress. A looped recording also reuses its timestamps without announcing a new session. Evidence: `bus/run.py:39–59`.

32. **Bench artefacts can claim more than was saved or counted.** Snapshot saving ignores the success result of `cv2.imwrite`, then the tool announces snapshots in the output directory. The floor command counts messages from its final flush but does not add that final message's people or IDs to its summary, understating its statistics. Evidence: `tools/bench_detect.py:80,91`; `floor/run.py:106–117`. These are development faults, but the artist may rely on those reports when judging readiness.

33. **Automatic calibration can save a poor fit as usable.** It filters boxes by confidence and position but not by camera name; a mixed-camera recording can be combined accidentally. It neither checks the optimizer's success flag nor rejects excessive fitted errors before writing the homography. A pixel error is not a measured error in floor metres. The horizontal `u` argument to `predicted_box_height()` is unused; its vertical-angle approximation and assumed person height are not evidence of venue accuracy. Evidence: `tools/calibrate_auto.py:44–69,84–95,114–138`. It prints errors, so they are inspectable, but no pass/fail judgement is made.

34. **Configuration omissions and old recordings are accepted inconsistently.** Missing `n_smooth` silently falls back to raw headcount; missing actions often become zero. Other missing fields raise. Unknown mood labels are omitted from the total. There is no message version or startup check linking sensing's four ring thresholds with the controller's ring map. Evidence: `cockaigne_controller/loop.py:69–75`; `cockaigne_controller/bandit.py:98–109`; `features/crowd.py:273–280`; `config/sensing.yaml:56–57`; `config/controller.yaml:25`. The resulting mixture of permissive defaults and hard crashes makes failures difficult to interpret.

35. **Installation and rehearsal instructions omit required inputs.** There is no `pool.json` in the repository, although `RUNBOOK.md:26` asks the reader to supply it. The saved-layout loader then opens that path directly (`cockaigne_controller/run.py:55`). There is no checked-in detector weight file or offline preparation check; `.gitignore:1–2` anticipates downloading weights on first run, while `detect/tracker.py:36` simply asks YOLO to load them. These omissions normally fail visibly at setup, but there is no unattended recovery. They also prevent the documented rehearsal and offline show startup from being a complete procedure as supplied.

36. **The dependency declaration allows a version that cannot import this code.** `pyproject.toml:11` allows `websockets>=12.0`; `bus/publish.py:16` requires `websockets.asyncio.server`. I downloaded and inspected the Windows Python 3.12 wheel for version 12.0: it has no `websockets/asyncio/` package. The controller also imports the new client API at `cockaigne_controller/run.py:103`. This is a startup error rather than a silent exception, but nothing in the repository pins the working environment or restarts a failed deployment. All dependency requirements are open-ended, so the successful environment below is not reproducible from a lockfile.

37. **The controller's clock can slip without a timing-fault report.** It awaits bus publication on the same path that schedules the next clip, with no application send deadline. A connection that stalls instead of closing can delay subsequent ticks. Synchronous ledger and log writes can also delay the loop. Confirmation's deadline is checked before a sleep and REST call, so the call can finish after the nominal deadline; the promised two seconds is not a strict overall bound. After a retry, the clip clock still runs from the earlier initial fire time. Evidence: `cockaigne_controller/run.py:73–88,171–196`; `clock.py:17–31`. These delays are not measured or reported as late playback, and the healthy-clock unit test does not exercise them.

Two distinctions matter. The caught `OSError`/connection-closed branch in the controller does log a generic reconnect warning afterwards; it is not wholly silent (`cockaigne_controller/run.py:114–118`). REST confirmation errors also log warnings (`cockaigne_controller/run.py:79–88`). Their problems are loss of detail, incomplete recovery and continuing to claim a fire, rather than absence of all logging. Intentional blank-line/stream filtering in replay, ignoring non-crowd messages in the controller, and not echoing a message to its sender are ordinary behaviours; they become faults only if operators mistake them for universal delivery or validation.

**Every Python file, in plain English.** Each paragraph states what enters, what happens, and what leaves. “Import” means making a component available to another Python file; it does not mean that the gallery process has been started. Line counts include blank lines and comments.

**`cockaigne_sensing/__init__.py` — 0 lines.** This is an empty package marker. It accepts no input, performs no work and produces no output. In particular, importing the sensing package does not open cameras or launch the sensing chain.

**`cockaigne_sensing/config.py` — 11 lines.** Given an optional settings-file path, this opens that file, or the repository's default sensing settings, and turns its YAML text into a dictionary of values for other components (`5–11`). Its output is settings, not measurements. It neither fills missing settings nor checks that numbers make sense; unreadable files and parsing errors propagate to its caller.

**`cockaigne_sensing/capture/__init__.py` — 9 lines.** This makes the single-source reader and Reolink address builder available under the shorter capture-package name (`7–9`). It takes no frames or camera list itself, and produces no observations. Its introductory description explains the common timestamp-and-picture format used by live sources and recordings.

**`cockaigne_sensing/capture/source.py` — 77 lines.** An address builder accepts a camera address, username, password and stream choice and produces an RTSP URL (`24–31`). `FrameSource` accepts a URL or file path, opens it with OpenCV, optionally skips frames, and yields a time plus a colour image (`37–74`). Files get times calculated from frame count and reported frame rate; cameras get local arrival times. Live read failures trigger silent reopening; file read failures end the iterator. `close()` releases the capture object.

**`cockaigne_sensing/detect/__init__.py` — 9 lines.** This exposes the person tracker and camera-message builder for other modules (`7–9`). It accepts no measurement itself and starts no detector. Importing it also imports the tracker implementation and its external detector library; that library is therefore needed even for callers interested only in the message helper.

**`cockaigne_sensing/detect/tracker.py` — 79 lines.** One tracker takes one camera's pictures and times, runs YOLO's person detector and ByteTrack, remembers when each ID first and last appeared, and returns sufficiently old tracks with rectangles and confidence (`26–68`). `tracks_message()` adds the camera name, image dimensions and time and produces the JSON-compatible camera-tracks message (`71–79`). It does not transform positions into metres. It offers no camera-health output when detection returns nothing.

**`cockaigne_sensing/floor/__init__.py` — 41 lines.** This is mostly an explanation of the intended floor pipeline and the incomplete marker-calibration tool (`1–38`). It exposes the floor tracker, sighting type and people-message builder (`39–41`). It consumes no observations or files on its own and emits nothing; importing it does not perform calibration or camera merging.

**`cockaigne_sensing/floor/camera.py` — 87 lines.** This describes an ideal camera by its position, height, direction, tilt and focal length (`24–34`). It turns that description and floor coordinates into picture coordinates, estimates focal length from field of view, and builds the reverse picture-to-floor matrix (`36–87`). Outputs are numerical points and a matrix for calibration tools. It ignores lens distortion, and any direction string other than the recognized forward choice is treated as the reverse direction; the public class does not validate that choice.

**`cockaigne_sensing/floor/homography.py` — 31 lines.** This loads the stored picture-to-floor matrix, chooses the bottom centre of a person's rectangle as the feet, and transforms that pixel point into metres (`15–31`). Input is a calibration file or rectangle/point; output is a matrix or coordinate pair. It ignores the calibration file's explanatory metadata. A mathematically undefined conversion returns not-a-number coordinates instead of an explanation or warning.

**`cockaigne_sensing/floor/tracker.py` — 166 lines.** Given timed floor sightings, this combines nearby sightings, predicts where existing people should be, matches nearest observations, adds new people and eventually forgets missing ones (`42–119`). It briefly continues reporting a missed person at a predicted position and estimates velocity from recent positions (`121–144`). The message builder produces floor dimensions and each person's ID, position, motion, age and rectangle shape, with placeholder mood/action fields (`147–166`). It cannot tell which camera or original detector ID a sighting came from.

**`cockaigne_sensing/floor/run.py` — 121 lines.** `FloorStage` accepts camera-track messages and settings, loads available calibration matrices, rejects positions outside its floor allowance, groups close timestamps and returns people messages (`30–86`). The command-line wrapper reads a tracks recording, feeds this stage, appends results to an output recording and prints a summary (`89–117`). It supplies an explicit final flush at file end. This is a file-processing command, not the missing live multi-camera launcher.

**`cockaigne_sensing/features/__init__.py` — 46 lines.** This both documents the scoring approach and defines a small coordinator (`33–43`). Given settings and then a people message, it runs the per-person scorer, modifying posture, arousal and valence in that same message, then runs crowd scoring. Its output is the augmented people message and either a crowd message or no crowd update yet. Unlike most initializer files, this one contains a real stage of the processing chain.

**`cockaigne_sensing/features/crowd.py` — 299 lines.** This takes people positions, velocities, ages, action scores and mood labels. It calculates proximity, aligned motion, stillness and viewing-spot/dwell proxies, smooths headcount and score, and gradually fills or drains the reservoir that chooses a ring (`47–258`). It also compares current action frequency with a longer baseline (`260–285`). Roughly once per input-time second it returns the crowd message, including counts and rounded scores (`286–299`); between those moments it returns no message. It has no independent timer or persistent storage.

**`cockaigne_sensing/features/person.py` — 156 lines.** This accepts each person's position, motion, rectangle and time, keeping a short history per ID (`54–98`). It writes posture, speed-based arousal and shrinkage/roughness-based valence into the input person, then returns one mood label per ID (`100–156`). Short path histories estimate whether someone is wandering; a minimum label lifetime reduces flicker. These are mechanical interpretations of geometry, not evidence of someone's actual feelings, and the output has no uncertainty flag.

**`cockaigne_sensing/features/run.py` — 52 lines.** This command accepts a people recording, output path and optional settings. It passes each input through `FeatureStage`, appends both the amended people messages and emitted crowd messages to the output, then prints counts and final/highest ring information (`20–48`). It does not publish to a live bus, open cameras or continue once the input file has finished.

**`cockaigne_sensing/actions/__init__.py` — 33 lines.** This is entirely a build brief. It describes a future component that would accept person crops, ask a local image-language model about phone/drink/eat behaviour, require repeated agreement and return action scores (`9–26`). As written, it accepts no input, calls no model and produces no action result. The crop matching, timing and failure behaviour of that future component cannot be explained from code because the code is absent.

**`cockaigne_sensing/bus/__init__.py` — 16 lines.** This exposes the ledger, event interpreter, WebSocket publisher, recorder and replay reader (`12–16`). It accepts no message itself and starts no server. Its exports let stages and the controller share those components, but importing it also requires the WebSocket implementation, even when a caller wants only file replay.

**`cockaigne_sensing/bus/record.py` — 57 lines.** `Recorder` accepts a path and message dictionaries and appends compact JSON lines; closing it completes buffered output (`18–30`). `replay()` accepts a recording path, optional stream filter and pacing choice, and yields decoded messages in file order (`33–57`). With real-time pacing it waits relative to the first selected message. It does not check the full message contract, sort timestamps, identify session boundaries or recover a damaged trailing line.

**`cockaigne_sensing/bus/publish.py` — 66 lines.** Given a permitted local host and port, this starts a WebSocket server and keeps a set of connected clients (`24–49`). It sends supplied message dictionaries to all clients and passes client-supplied text to everyone except the sender (`40–61`). Output is socket traffic; this component writes neither records nor ledger entries. It enforces local binding but does not inspect message content or report failed sends individually.

**`cockaigne_sensing/bus/ledger.py` — 71 lines.** The ledger accepts an event kind and fields and appends a timestamped JSON line to a file (`20–36`). `LedgerEvents` accepts crowd and people messages, writes changed requested rings, and records the start of each continuous above-threshold action (`39–71`). It does not record action endings, camera faults or whether a requested ring was actually displayed. The timestamp comes from the local wall clock, independent of the sensing message's time.

**`cockaigne_sensing/bus/run.py` — 78 lines.** This accepts a recording and settings, starts the bus, replays messages at their recorded pace, derives bus ledger events and optionally makes another recording (`28–59`). It can loop the file or stop at its end. Output is socket traffic and ledger/optional recording files. Messages received back from clients are rebroadcast by `Publisher` but are not included in this command's recorder or event derivation. This is the existing rehearsal bus, not a live sensing launcher.

**`cockaigne_sensing/tools/__init__.py` — 7 lines.** This is a comment-only directory description: no inputs, executable work or outputs. Its list is stale: it still calls the fake-room tool unwritten (`5`), although that implementation exists, and names a separate replay tool while replay service is actually available under `bus.run`. The marker-click calibration tool remains absent.

**`cockaigne_sensing/tools/bench_detect.py` — 95 lines.** Given a video/source, detector options and output directory, this reads sampled pictures, tracks people, prints counts, appends camera-track messages and saves annotated full-frame JPEGs (`30–91`). Outputs are both data and identifiable imagery. Snapshots are on by default without `--record`. This tool provides useful detection inspection, but its rate defaults, indefinite per-ID history lists and recording behaviour make it unsuitable as an unattended gallery launcher.

**`cockaigne_sensing/tools/calibrate_auto.py` — 143 lines.** Given a recording of rectangles, camera direction, assumed person height and known floor/picture points, this keeps selected boxes and fits camera height, tilt and setback (`44–95`). It derives and saves a picture-to-floor matrix and prints pixel fitting errors (`98–139`). This is an approximation for bench footage, not a measured-marker calibration. I can follow the calculation, but the repository does not justify the precise fitting weights, demonstrate the claimed metre accuracy, or define a maximum acceptable error.

**`cockaigne_sensing/tools/fake_room.py` — 177 lines.** This describes people moving between timed waypoints in four scenarios, optionally combines them, adds small repeatable positional jitter and emits people messages with placeholder scores (`40–152`). The command writes a chosen scenario to a recording (`155–173`). Inputs are scenario, seed and floor settings; output is fabricated tracking data, not real sensing. The separate scenarios are usable test inputs, but the combined day preserves infinite lifetimes and reuses IDs, corrupting the recommended full rehearsal.

**`cockaigne_sensing/tools/plan_view.py` — 80 lines.** This accepts a people recording, optional title/camera marker and output path, collects positions per person ID, then draws their paths on a floor rectangle and saves an image (`27–76`). Short tracks are drawn faintly. It does not verify whether a path is physically correct, and it joins all occurrences of an ID, so reused IDs or appended sessions can produce misleading paths. An empty/non-people file leaves no floor and raises rather than producing a useful explanation.

**`cockaigne_controller/__init__.py` — 16 lines.** This makes the clip map, name parser, clock and decision engine available for import (`12–16`). It takes no crowd messages itself and starts neither the control loop nor Resolume. Its description locates the actual live loop in `run.py` and the decision rules in `loop.py`.

**`cockaigne_controller/config.py` — 12 lines.** This accepts an optional YAML path and returns controller settings, defaulting to the file next to the source packages (`6–12`). Its output is a dictionary with no validation. It does not confirm that addresses are local, ring settings agree with sensing, timing values are positive, or configured layers and arms exist.

**`cockaigne_controller/clipmap.py` — 116 lines.** This reads move names such as a move from Barren to Machinery 1, separates their source and destination, and builds dictionaries of moves and loops (`20–63`). Given two nodes it can return a clip or the first step of a shortest available route (`68–94`). It also produces human-readable missing-pool complaints (`96–116`). It works from names alone and cannot prove that media exists, routes preserve a ring, or every special-case move assumed by the controller is present.

**`cockaigne_controller/clock.py` — 34 lines.** This takes clip length, audio lead and caller-supplied times. After remembering when a clip was fired, it answers whether the next audio preparation or clip fire is due, with a flag to avoid preparing audio twice (`10–34`). Its outputs are yes/no answers. It does not sleep, send commands, read wall-clock dates or inspect actual playback, so correctness depends on the caller reporting a successful start accurately.

**`cockaigne_controller/bandit.py` — 118 lines.** This is the learning chooser: it remembers numerical beliefs about each visual arm for each audience-size band, draws a random score per arm, adds action influence and ranks the results (`27–73`). Separate helpers turn cohesion change into a reward and derive an action influence from rates and sitting counts (`22–24,76–118`). Inputs are settings, crowd measurements, rewards and optional repeatable randomness; outputs are arm rankings, reasons and updated internal beliefs. The action influence has no final cap and only ages when observations arrive.

**`cockaigne_controller/personality.py` — 34 lines.** Given a date and settings, this chooses a personality by the day-of-year's remainder when divided by the number of configured personalities (`20–23`). It turns that personality's strength and Storm preference into initial success/failure numbers for each arm (`26–34`). It outputs a name, parameter set and initial beliefs. It does not schedule midnight changes itself; the running controller must call it on date changes.

**`cockaigne_controller/loop.py` — 189 lines.** This holds the imagined current wall position, most recent crowd measurements, action influence, daily beliefs and pending reward (`40–61`). It accepts crowd updates, dates, fire times and requests for the next decision; it returns a decision message and a Resolume layer/slot (`65–189`). It decides a destination from ring and arm, finds a route, and awards earlier choices when cohesion changes. It does no network work, but advances its position before network success and confuses requested ring with displayed ring during blind descent.

**`cockaigne_controller/audio.py` — 16 lines.** Given a Resolume connection, settings and ring number, this computes ring divided by maximum ring and sends that same volume to every bank-A audio layer (`12–16`). Output is four volume commands with the supplied defaults. It does not receive an arm, start a stem or operate a transition. Its opening description correctly calls it a stub; it cannot produce the full audio behaviour described in the guide.

**`cockaigne_controller/resolume.py` — 71 lines.** This accepts either composition/layer JSON or connection settings. It extracts clip names and slots, reads the local REST composition, identifies a connected slot, and sends OSC clip-connect and volume messages (`14–71`). Its outputs are a layout, a slot number or network commands. The REST connection-status formats are assumptions documented in the function and tested with synthetic examples; this repository supplies no real Resolume response proving the installed version uses those formats.

**`cockaigne_controller/fake_resolume.py` — 60 lines.** This starts a local UDP listener, records every OSC address and argument it receives, and normally prints them (`19–43`). The command runs it on the configured test port until interrupted (`46–56`). Input is OSC traffic; output is an ever-growing in-memory list and terminal text. It does not play video, expose a REST layout, acknowledge playback or simulate a restart, so successful traffic to this fake does not verify those real-world behaviours.

**`cockaigne_controller/run.py` — 218 lines.** This is the live controller wrapper. It loads a saved or REST layout, checks it, creates the decision engine, clock, log and ledger, and starts a background bus reader (`131–157`). It then checks the date and blindness, prepares the next decision/audio, fires video, attempts confirmation, publishes the decision and records outcomes (`159–201`). Inputs are settings, crowd traffic and Resolume responses; outputs are OSC/WebSocket traffic, logs and ledger/optional recordings. This is where the unmonitored reader, incomplete fire protection and separation between planned and actual state matter most.

**`tests/test_record_replay.py` — 21 lines.** One test creates two synthetic camera messages, writes them through the recorder and reads them back, checking equality and stream filtering (`6–21`). Input is a temporary path and fabricated tracks; output is pass/fail assertions and a temporary recording. It does not test real-time pacing, abrupt interruption, duplicate sessions or malformed trailing data. Importing the track helper also imports Ultralytics, although no model runs.

**`tests/test_floor.py` — 100 lines.** Seven tests feed ideal camera geometry, synthetic walkers, missed observations and the committed venue-A tracks into the floor components (`17–100`). Assertions check geometric round-trip, stable ID for one easy walker, merging, coasting, bounds rejection and a broadly populated fixture result. Inputs include temporary calibration files; outputs are assertions, not a displayed installation. There is no test of distinct close people, swapped IDs, expired tracks revived after a silent gap, wrong-resolution calibration or four asynchronous cameras.

**`tests/test_features.py` — 224 lines.** Fifteen tests build imagined rooms and feed them through scoring, checking occupancy ceilings, reaching/draining rings, smooth reservoir changes, synchrony, posture and mood holding (`42–207`). A final test launches the feature command as a subprocess and checks both output streams (`210–224`). Inputs are synthetic people and times; outputs are assertions and temporary recordings. These establish selected mathematical behaviours, not real-world mood accuracy, camera-derived noise tolerance in general, or fault recovery.

**`tests/test_fake_room.py` — 63 lines.** Five tests inspect the separate lone, group, sitting and leaving scenarios, checking velocity consistency and expected broad feature outcomes (`22–63`). Inputs are generated actor messages; outputs are assertions after feature scoring. It does not call the combined `day` scenario in a test, which is why duplicate IDs, never-ending earlier actors and the wrong stated duration pass unnoticed.

**`tests/test_bus.py` — 107 lines.** Six tests check sequential ledger reopening, ring-change and action-event derivation, rejection of an external bind address, and two healthy local WebSocket exchanges (`22–107`). Inputs are made-up messages and local sockets; outputs are assertions and temporary ledger files. There is no failed-send, slow-listener, disconnect/reconnect, concurrent-writer, lost-startup-message, empty-loop or bus-recording-of-client-traffic test.

**`tests/test_controller.py` — 249 lines.** Thirteen tests create a made-up pool of clips and check parsing, missing-pool reports, routes, fixed-arm movement, blind descent, clock timing, layout extraction, local OSC reception and selected confirmation failures (`15–249`). Inputs are fictional layouts, timestamps, crowd states and fake network peers; outputs are assertions. Its blind example starts with actual and requested ring aligned. Its confirmation test never makes the OSC send itself fail, and it does not test the actual perpetual controller loop or reader supervision.

**`tests/test_bandit.py` — 154 lines.** Nine tests give the chooser rewards, action rates and dates and check learning, chosen examples of bias/decay, sitting baseline, daily resets and reward bookkeeping (`21–154`). Inputs are synthetic measurements and repeatable random seeds; outputs are assertions and one temporary ledger. The tests do not establish a universal bound on action influence, decay with no messages, clean ownership of a reward across midnight, or the live loop's five-second-early settlement.

**Where the code could be plainer.**

- **Separate choosing, sending and confirmed playback.** At present `decide()` changes the wall position, ends the previous reward and opens the next reward before a clip is sent. `fired()` later patches its time, while the outer loop carries another pending decision. That makes a simple question—what is actually on the wall?—hard to answer. A small explicit sequence with separate planned and confirmed positions would be easier to read and would remove several failure ambiguities. Sources: `cockaigne_controller/loop.py:116–131,147–189`; `cockaigne_controller/run.py:171–195`.

- **State the artistic movement rules directly.** Breadth-first route search is a standard, understandable algorithm. The unnecessary subtlety comes from letting an arbitrary shortest route stand in for holding a ring or retreating safely, then adding probe, loop and runner-up exceptions. Define which moves preserve a ring and which moves are permitted during a fault, and validate those exact rules at startup. Sources: `cockaigne_controller/clipmap.py:77–116`; `cockaigne_controller/loop.py:149–175`. This need not become a larger framework.

- **Make numerical claims and unavailable measurements explicit.** The code has several meanings for zero, an empty list, no message and a default score. Those can mean nobody is present, an action recognizer is absent, a camera was ignored, a frame lacked IDs, or a score was not due yet. A few explicit status fields and small input-checking functions would be plainer than expecting every consumer to infer those meanings. Sources: `floor/run.py:54–56`; `floor/tracker.py:161–163`; `features/crowd.py:255–258`; `cockaigne_controller/loop.py:69–77`.

- **Give shared events one clear owner and one time convention.** A reader must currently reconcile two ledger writers, bus-only event derivation, a recorder that misses client traffic, recording-relative timestamps, arrival timestamps and planning timestamps. One documented event-writing route and an explicit distinction between measurement, decision and playback time would make the installation much easier to diagnose. Sources: `bus/run.py:33–52`; `bus/publish.py:40–61`; `cockaigne_controller/run.py:178–188`. The current arrangement has fewer lines but hides important distinctions.

- **Move executable work out of package introductions and avoid heavyweight imports for message helpers.** Most `__init__.py` files merely expose names; `features/__init__.py` also implements a stage. A recorder-only caller imports the WebSocket module, and the two-message recording test imports the detector library merely to build data. Naming those small components directly would make dependencies and startup failures easier to understand. Sources: `features/__init__.py:29–43`; `bus/__init__.py:12–14`; `detect/tracker.py:13`; `tests/test_record_replay.py:2–3`.

- **Simplify calibration and rehearsal before adding more inference.** The automatic fit combines assumed body height, an ideal camera, selected rectangles and hand-weighted error terms; the mood interpretation then adds more assumptions to those positions and rectangles. For a fixed gallery, measured calibration points and a clearly bounded rehearsal are easier to verify. The random learning chooser itself is part of the stated artistic design; removing it is not necessary to make the failure handling plain. Sources: `tools/calibrate_auto.py:60–95`; `features/person.py:86–156`; `tools/fake_room.py:113–120`.

I can explain the execution of the implemented functions. What I cannot explain from this repository is the empirical justification for the exact mood thresholds, the fit's error weights, the claimed quarter-to-half-metre calibration accuracy, or the assumed real Resolume connection-status representation. There is no supplied measurement or real API fixture establishing those claims. The missing actions implementation, marker-calibration tool and live launcher cannot be explained beyond their briefs. These are evidence gaps, not successful validations.

The repository is already small: 2,891 physical Python lines in the two packages, plus 918 in tests. No Python file exceeds 300 lines; the largest is `features/crowd.py` at 299. The controller folder contains 884 physical Python lines, within the 1,000-line module budget; each sensing folder is smaller. A conservative count retaining docstrings but excluding blank and comment-only lines is 2,376 across both packages. The problems are not caused by a large framework or deep inheritance. They arise from implicit state, missing connections and promises that are stronger than the implementation.
